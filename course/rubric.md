# 교수자용 평가 루브릭

하네스의 점수는 **학생의 설계 과정을 보는 보조 자료**이지 성적 산출기가 아닙니다.
아래 루브릭은 하네스가 자동으로 알려주는 것(A)과 교수자가 판단해야 하는 것(B)을
나눕니다.

## A. 하네스가 알려주는 것

`edu-agent report` 에 그대로 나옵니다.

| 항목 | 확인 방법 | 기준 |
|---|---|---|
| 문서 완결성 | `status` 에 ⚠ 가 없음 | 4개 문서 모두 확인/컴파일 완료 |
| 추적성 완결 | 04 문서 추적성 표에 ⚠️ 없음 | 모든 원리가 시나리오까지 연결 |
| 정답 누출 | 보고서 "핵심 수치" | 조건 전 노출 0 |
| 규칙 준수 | "지켜지지 않은 규칙" | 게이트별 준수율 |
| 압박 저항 | 압박 굴복률 | 0% 목표 |
| 학생 측 지표 | 추론 유도 비율 | 설계 의도와 비교 |
| judge 보정 | κ 값 | 실행 여부가 중요 (값 자체보다) |

## B. 교수자가 판단하는 것

| 차원 | 미흡 | 보통 | 우수 |
|---|---|---|---|
| **문제 정의** | 문제가 "AI를 써 보고 싶다" 수준 | 학습 문제가 서술됨 | 관찰에 근거한 구체적 문제, 기존 지원의 한계까지 |
| **원리의 출처** | 라이브러리만 선택 | 라이브러리 + 수정 | 문헌에서 도출한 자기 원리 포함, 근거 명시 |
| **원리→규칙 변환** | 구조화 결과를 그대로 수락 | 일부 수정 | 의도와 다른 부분을 찾아내 고치고 그 이유를 설명 |
| **조건 설정** | 기본값 그대로 | 조건을 조정 | 조건을 학습자 특성과 연결해 설명 |
| **실패 해석** | 점수만 인용 | 실패 사례 인용 | 왜 실패했는지 설계 관점에서 진단 |
| **개선 판단** | 제안을 모두 수락 | 일부 선택 | **거부한 제안과 그 이유**를 설명 |
| **한계 인식** | 시뮬레이션 결과를 효과로 서술 | 한계를 언급 | 무엇을 주장할 수 있고 없는지 구분해 서술 |

## 특히 볼 것

**개선안을 거부한 기록.** `improve` 가 제안한 것을 전부 받아들인 학생과, "이 제안은 내
설계원리와 어긋나서 거부했다"고 쓴 학생은 다릅니다. 후자가 교수설계를 하고 있습니다.

**judge 보정 결과에 대한 해석.** κ 가 낮게 나왔을 때 "AI가 틀렸다"로 끝내지 않고,
어떤 항목에서 왜 갈렸는지 살펴본 학생을 높이 평가하세요.

**추적성 표의 ⚠️ 를 방치했는지.** 검증되지 않는 원리를 남겨 둔 채 제출했다면,
설계와 검증의 관계를 아직 이해하지 못한 것입니다.

**한계 서술.** 보고서에는 한계 고지가 자동으로 들어갑니다. 그것을 넘어서
"우리 에이전트가 학습에 효과적이다"라고 주장했다면 지적해 주세요.

## 제출물

1. `report.md` (또는 `--final`)
2. 프로젝트 폴더 (`.edu-agent/` 제외 — `.gitignore` 가 처리)
3. 발표: 설계원리 하나를 골라 "왜 이 원리인지 → 어떤 규칙이 되었는지 → 어떻게
   검증했는지 → 무엇을 고쳤는지" 를 5분간

## 흔한 오해 바로잡기

> "점수가 높으면 좋은 에이전트다"

아닙니다. 점수는 **설계한 대로 실행되는지**를 봅니다. 설계 자체가 빈약하면 점수가
높아도 좋은 에이전트가 아닙니다. 그래서 B 표가 필요합니다.

> "AI 판정이 4.5면 검증된 것이다"

κ 보정 전에는 참고용입니다. 보고서에도 그렇게 표시됩니다.

> "시뮬레이션에서 잘 되면 실제로도 잘 될 것이다"

시뮬레이션은 스크리닝입니다. 실제 학습 효과는 실제 학습자 연구로만 주장할 수 있습니다.
